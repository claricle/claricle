== Purpose

Claricle is a Ruby library and CLI for working with image files. It
detects a file's format from its bytes and gives one object and one set
of models to work with, wrapping specialist tools behind a single API.

Format detection ships today. Inspection, conformance checking and
conversion are being built on top of it.

[NOTE]
====
Version 0.1.0 was a name reservation. Its `validate`, `convert` and
`compress` commands printed "coming soon" and did nothing; they have
been removed rather than left in place. Its metadata also advertised
image compression, which was never implemented -- compression is not in
v1's scope. Rendering, editing and WMF conversion are likewise outside
v1.
====

== Etymology & Symbolism

*Claricle* = *Clari* (clarity) + *cle* (particle)

*Combined:* "Clear particle" or "Bright essence"

The name reflects what the library is for:

* *Detection* -> know exactly what a file is
* *Validation* -> clarify every pixel
* *Conversion* -> preserve the clear essence
* *Ruby* -> gem-like, small but brilliant

== What works today

* Format detection for PNG, SVG, EMF, WMF, EPS, PS and PDF
* `inspect` for EMF -- dimensions, DPI and header metadata
* `inspect` for PNG -- dimensions, colour space, bit depth and DPI
* `inspect` for SVG -- dimensions from the root, absolute units
  converted to CSS px; a relative unit such as `%` reports no dimension.
  It stops at the root start tag, so its parse status means "the root
  was readable", not "the document is well-formed". A file damaged
  after that tag still reports `ok`. Judging the whole document is
  conformance, and no handler implements it yet
* `inspect` for EPS and PS -- dimensions from a **concrete bounding box
  declared in the DSC header**, preferring `%%HiResBoundingBox` and
  falling back to `%%BoundingBox`, plus the title, creator, creation
  date and language level. Only the header is parsed. A box is reported
  only when the parser reads the same values the file's **first**
  declaration spells out in DSC syntax. A box that fails that check is
  discarded rather than guessed at -- the other box, if the file
  declares one, is still used, and dimensions are nil only when neither
  survives. The page count is deliberately not
  reported: the parser fills it in only for the two-argument
  `%%Pages: n m` form, so it would be present for some files and absent
  for others with nothing in `meta` to tell the cases apart
* `formats`, listing each format and what Claricle can do with it
* `Claricle::Image`, built from a path or from bytes
* A unified issue and report model, serialising to and from JSON
* An error taxonomy mapped to documented CLI exit codes

== What does not work yet

* `inspect` for WMF and PDF -- EMF, PNG, SVG, EPS and PS have handlers
  so far, so the rest raise `Claricle::UnsupportedFormat`
* **`(atend)` bounding boxes for EPS and PS.** The value lives in the
  trailer, and resolving it needs the nested-document and data-section
  handling that reading only the header exists to avoid. Such a file
  inspects as `ok`, and its dimensions come from a concrete
  `%%HiResBoundingBox` beside it or from nothing at all
* **CR-only line endings for EPS and PS.** The parser reads no DSC
  comments from them, so those files inspect as `ok` with no dimensions
  and no metadata
* `conform` and `convert` for every format. No handler implements
  either yet, so both raise `Claricle::UnsupportedFormat`. `claricle
  formats` reports this per format, and it reads the handlers rather
  than a list, so it cannot claim an operation that is not there.
  The `conform` command and `Claricle.conform?` do exist -- they take
  files, expand globs and report per file -- but every format currently
  answers exit 3, so the command is plumbing waiting on its handlers
* `--profile` for `conform`. PDF and SVG will name stricter standards
  through it, but no handler defines one yet, so supplying `profile:`
  is refused rather than accepted and ignored
* WMF beyond detection. `detect` returns `:wmf`, but no handler
  registers it, so every operation on a WMF raises
  `UnsupportedFormat`. That is deliberate: the upstream parser this
  library would use reports "WMF parser not yet implemented"

== Command Line Interface

=== Available commands

[cols="1,3"]
|===
| Command | What it does

| `claricle inspect FILE` | Report a file's format and metadata
| `claricle conform FILE...` | Check files against their format's conformance rules
| `claricle formats` | List the formats Claricle handles, and what it can do with each
| `claricle version` | Print the version
|===

`claricle help` lists these, plus the commands Thor contributes itself.

The operations are added as they are implemented, so this table never
lists a command that does nothing.

`claricle inspect` prints a file's own metadata under `meta.` keys, and
shows control characters escaped. Both are there so a crafted file
cannot print a line that looks like Claricle's own. `--json` is
unaffected: it carries the real values.

=== Version

[source,sh]
----
$ claricle version
Claricle version 0.1.0
----

=== Exit codes

[cols="1,4"]
|===
| Code | Meaning

| 0 | Success
| 2 | Bad invocation -- unknown command, wrong arguments, missing file
| 3 | The format is unknown, or is recognised but unsupported for that operation
| 4 | The operation failed, or something unexpected went wrong
|===

A command may also exit with a status of its own choosing. A status in
0-255 is passed through unchanged; one outside that range becomes 4,
because a process status has to be a byte. The codes above are the ones
this library assigns.

Exit code 1 is reserved for a nonconformant file. `claricle conform`
ships, but no handler judges conformance yet, so it reaches 2 and 3
today and 1 becomes reachable with the first handler.

`claricle conform` takes any number of files. A positional is a literal
path when it names an existing file and a glob otherwise, and
`--pattern` reads its argument as a glob whatever the filename looks
like -- which is how a file genuinely called `star[1].png` stays
reachable both ways. A pattern adds to the positionals rather than
replacing them, the combined set is deduplicated and processed in
sorted order, a file that fails does not stop the ones after it, and
the command exits with the highest code any of them reached. Matching
no files at all is a bad invocation, not a silent pass. `--json` always
emits an array, a single file included, so a consumer never gets one
shape for one file and another for many.

== Usage

Detect a format from a path or from bytes:

[source,ruby]
----
require "claricle"

Claricle.detect(File.binread("logo.png"))   # => :png
File.open("logo.png", "rb") { |io| Claricle.detect(io) } # => :png

image = Claricle::Image.from_path("logo.png")
image.format    # => :png
image.content   # read lazily, once
----

`Image.from_path` streams the file while detecting. `Claricle.detect`
accepts a String of bytes or an IO; an IO is read from wherever it
currently sits and is never rewound.

Detection reads the IO in chunks and reclassifies after each one, so it
stops on the first chunk that settles the format and never reads past
that chunk. Each read asks for the whole remaining probe allowance --
the most any detector probe consults -- so how far the IO advances is
set by how much the source hands over per read. A file or a `StringIO`
hands over the whole allowance at once, so a source longer than the
allowance is read that far even though a PNG signature settled it after
eight bytes. A pipe or a socket hands over what has arrived, so a short
complete image settles without waiting for bytes nothing needs.

A source beginning `%!PS` is the exception. `:ps` and `:eps` are told
apart by scanning the first line, and a byte that has not arrived yet
can still flip one into the other, so that verdict always reads to the
allowance or to the end of the stream.

Detection never reads beyond the allowance, and it leaves what it did
not read on the IO: after a source longer than that, the IO sits
mid-stream and `eof?` is false. A caller who needs the rest of the
stream, or cares whether it reached EOF, should check rather than
assume.

An SVG is recognised only when its root carries the SVG namespace. A
bare `<svg>` with no `xmlns` is not detected, because SVG requires that
declaration and the probe will not guess at one.

Bytes matching no known signature raise `Claricle::UnknownFormat`. A
format that is recognised but unhandled raises
`Claricle::UnsupportedFormat` -- two different answers to two different
questions.

Hand a delegate a real path, whichever way the image was built:

[source,ruby]
----
Claricle::Image.from_content(bytes, format: :png).with_path do |path|
  # a temporary file exists here, and only here
end
----

Hand it a source instead when the reader only needs a prefix:

[source,ruby]
----
Claricle::Image.from_path("logo.svg").with_source do |source|
  # the open file here; the bytes, for a content-born image
end
----

A path-born image is never slurped to satisfy `with_source`. That is how
the SVG handler reads the root, so a 64 MiB file costs the 8 KiB it
actually reads.

== Architecture

[source]
----
lib/claricle/
  version.rb           # VERSION
  detector.rb          # magic-byte and XML-root format detection
  image.rb             # the object every operation takes
  registry.rb          # frozen format -> handler map
  handlers/base.rb     # what a handler subclasses
  handlers/metafile.rb # EMF header metadata
  handlers/png.rb      # PNG metadata
  handlers/postscript.rb # EPS and PS DSC header metadata
  handlers/svg.rb      # SVG root metadata
  models/              # Location, Issue, Report, Inspection, BatchItem
  batch.rb             # one file set, one envelope per file
  fault.rb             # an exception's exit code and renderable message
  errors.rb            # Error, UnknownFormat, UnsupportedFormat, ...
  cli.rb               # Thor CLI and the exit-code Runner
----

`Detector`, `Registry`, `Batch`, `Fault`, `Handlers::Base`,
`Models::Base`, `Models::FreeFormHash`, `Models::UncoercedInteger`,
`Models::Validation`, `Models::Location::POSITIONS`,
`Models::BatchItem::CODES`, `Cli::Runner::Status::RANGE` and
`UnsupportedFormat::ABSENT` are private constants.
The public surface is `Claricle.detect`, `Claricle.conform?`,
`Claricle.conformance_report`, `Claricle.conformance_batch`,
`Claricle::Image`,
`Claricle::BatchResult`,
`Claricle::Cli` (including `Cli::Runner` and `Runner::Status`),
`Claricle::VERSION`, the error classes, the model classes
`Models::BatchError`, `Models::BatchItem`, `Models::Inspection`,
`Models::Issue`, `Models::Location` and `Models::Report`, and the two
vocabularies those models validate against,
`Inspection::PARSE_STATUSES` and `Issue::SEVERITIES`.

=== Adding a format

Not one file. A new format costs:

. a handler class under `handlers/`, declaring its formats
. a `require_relative` for it in `registry.rb` -- there is no autoloading
. an entry in `Registry::HANDLER_CLASSES`, next to that require
. a probe in `Detector` -- detection is one ordered sequence, not a
  per-handler sniffer, because the probes are heterogeneous and their
  order is load-bearing
. for an inbound conversion, an entry in the source handler's target
  list together with its feature-loss rules. Neither exists in `lib/`
  yet; both arrive with `convert`

== Installation

Add this line to your application's Gemfile:

[source,ruby]
----
gem 'claricle'
----

And then execute:

[source,sh]
----
$ bundle install
----

Or install it yourself as:

[source,sh]
----
$ gem install claricle
----

== Development

After checking out the repo, run `bin/setup` to install dependencies.
Then, run `rake spec` to run the tests.
You can also run `bin/console` for an interactive prompt that will allow you
to experiment.

To install this gem onto your local machine, run:

[source,sh]
----
$ bundle exec rake install
----

To release a new version, update the version number in `version.rb`, and then
run:

[source,sh]
----
$ bundle exec rake release
----

This will create a git tag for the version, push git commits and the created
tag, and push the `.gem` file to https://rubygems.org[RubyGems.org].
